# Disk images: the disk, and its partitions

`hivepack::image` reads what a disk image holds: the block device in it, and the partitions the table at its start names. It is the layer every other part of a disk image stands on, and it is **not a port** — there is no library behind a partition table. A master boot record's layout is the one every system has agreed on since MS-DOS, and a GUID partition table's is the UEFI specification's (version 2.10, §5.3, "GPT Disk Layout"). The repository's own MIT license covers the module, which is why it has no `LICENSE` of its own, unlike the ports beside it.

It reads a raw image — an `.img`, a `.bin`, a `dd` of a card — and the four containers that keep a disk in less room than it is long: **VHD** (`.vhd`, QEMU's `vpc`), **QCOW2** (`.qcow2`), compressed clusters and all, **VHDX** (`.vhdx`), what Hyper-V and WSL2 write, and **VMDK** (`.vmdk`), VMware's, which is one file or a descriptor naming several. What is **not** here yet, and the order it comes in, is in [issue #225](https://github.com/hivepaas/hivepack-rs/issues/225): the file systems a partition holds (FAT, ext2/3/4, NTFS).

**None of the containers is a port either**, and that is a choice worth writing down. QEMU's block drivers are the obvious reference and are GPL-2.0, which a module ported from them would carry — hivepack is otherwise MIT and BSD, and `rar` alone is an exception. All four formats have published specifications instead: Microsoft's *Virtual Hard Disk Image Format Specification* and *VHDX Format Specification*, both under its Open Specification Promise; QEMU's own `docs/interop/qcow2.txt`, which is an interoperability specification written for other programs to implement; and VMware's *Virtual Disk Format*. So each is implemented from its specification and checked against `qemu-img`, which is a tool that is run, not code that is copied. NTFS is the one layer where this will not work: it has no published specification, and the only references are GPL-2.0 (ntfs-3g, and the kernel's ntfs3).

## What it gives

- **A `Disk`** is a size and reads at offsets, never a position, so one disk can be read from several threads, as the file systems inside it will be. `std::fs::File`, `[u8]` and `Vec<u8>` are disks; a container will be one over another.
- **`partitions(&disk)`** answers with the table, the sector size its numbers are counted in, and the partitions in the order the table holds them — or with **none**, for a disk that has no table at all. A file system written straight to a disk has none, and so has a file that is not a disk image: that is not an error.
- **`partitions_in(&disk, sector)`** is the same, in sectors the caller gives: 512 or more, a power of two.
- **`Vhd`** is the disk inside a VHD image, and a `Disk` itself, so the partitions of one are read as any disk's are. A fixed image is the file with its footer taken off; one that grows is read through its table of blocks, and a block that was never written reads as zeroes.
- **`Vhdx`** is the disk inside a VHDX image, and a `Disk` too. It is the only container here that says what a sector is on the disk it holds (`Vhdx::sector`), which is what `partitions_in` wants.
- **`Qcow2`** is the disk inside a QCOW2 image, and a `Disk` too. Clusters are found through two levels of tables, and one that was never written, or that the image says reads as zeroes, reads as zeroes; a compressed one is decompressed whole.
- **`Vmdk`** is the disk a VMDK holds, and a `Disk` too. It is the one container here that may be several files: `Vmdk::open` reads the kinds that hold a whole disk on their own, and **`Vmdk::beside(path)`** reads every kind, as it is given a path and can open the files a descriptor names in the folder it is in.
- **`Part`** is one partition as a disk of its own. What reads the file system in it sees nothing of the disk before it and nothing past its end.

## The rules it follows

- **A GUID partition table is read before a master boot record**, because a disk that has one keeps a master boot record in front of it that says so (one partition of type `0xEE` over the whole disk). A table is looked for at the second sector for both sector sizes a disk has, 512 bytes and 4096.
- **Both of a GUID partition table's copies carry a CRC-32**, over the header and over the array of entries, and both are checked. Where the one at the disk's start fails, the copy at its end is read instead; where both fail, the answer says so and no partitions are made up. The check is what tells a table from bytes that happen to start with `EFI PART`.
- **A disk that says it has a GUID partition table and has none fails.** Reading its protective master boot record as a table of its own would answer with one partition over the whole disk, which is not what is on it.
- **The last sector of a GUID partition table's entry is its own**, not the one after it, so a partition of sectors 2048 to 6143 is 4096 sectors long.
- **An entry of all zeroes is no partition**, and the numbers count over it: a GUID partition table's partitions are numbered as the systems that name them do, 1 upwards by the entry's place in the array, and a master boot record's are 1 to 4 for its own entries and from 5 for the logical ones.
- **An extended partition is not a partition anything is in.** Its entry starts a chain of extended boot records, each of which says where its own partition's data is, counted from that record, and where the next record is, counted from the extended partition. The chain is followed at most 128 steps, and a record already seen ends it with an error, so a chain that leads back into itself cannot be read for ever.
- **A partition that reaches past the end of the disk fails**, with its number, rather than being given to something that would then read nothing.
- **A GUID partition table says what a sector is; a master boot record cannot.** The table's header is looked for in the second sector of each size a disk has, 512 bytes and 4096, so where it was found says which the disk's are. A master boot record holds nothing that says it, and its own numbers cannot tell: counted in a smaller sector they come out smaller, so they fit the disk either way and only point at the wrong place. It is read in 512-byte sectors, which is what every tool reading an image file does and what every disk sold with one counts in.

  A disk whose sectors are its own is read by `partitions_in(&disk, sector)`, for a caller that knows the size from somewhere else. That somewhere is the container: VHDX records the logical sector size, VHD's geometry is in 512-byte sectors, and QCOW2 says nothing — so this is the hook the containers will hang on when they arrive.
- **What a partition holds is what the table says it holds, which is not what is in it.** `Kind::says` names the types met on a disk anyone opens, and answers nothing for the rest; what is in a partition is told by reading it.

## What a VHD is, of what matters to read one

- **The footer is at the end of the file**, 512 bytes of it, and every number in a VHD is big-endian. An image that grows keeps a copy of the footer at the start, which is read when the one at the end does not hold: its checksum — the ones' complement of the sum of its bytes — is what says whether it does, and is what tells a VHD from a file that merely starts with `conectix`.
- **A fixed image is the disk itself**, the footer apart. One that grows has a dynamic header (`cxsparse`, 1024 bytes) and a table of 4-byte entries, one for each block of the disk, each saying in sectors where that block's bitmap is. An entry of `0xFFFFFFFF` is a block that was never written, and reads as zeroes.
- **Each block has a bitmap before it**, of one bit for each of its sectors, its length rounded up to a whole sector. A block is 2 MiB in every image anything writes.
- **The bitmap is not what is read.** It says which sectors of a block have been written, and the specification leaves the rest undefined; a block is zeroes in the file where nothing was put in it, so the bitmap says nothing the data does not. QEMU does not read it either, which was measured rather than assumed: an image built with a block whose bitmap is all zeroes and whose data is not, converted by `qemu-img` 10.2.1, comes out as the data.
- **The size is the footer's, not what the geometry multiplies out to.** A footer holds both, and an image can say two things. hivepack reads the size, which is what Microsoft's own tools write, and the only one of the two that can hold a disk larger than a CHS geometry can count — 65535 × 16 × 255 sectors, about 127 GiB. QEMU's rule was measured on an image made to disagree: for a creator of `win ` (Hyper-V and disk2vhd) or its own `qem2` it reads the footer's size, and only for its own older `qemu` images does it take the geometry, which those were written with anyway, so the two agree in every file that was not made to disagree.
- **A VHD's disk is not as long as what went into it.** `qemu-img` rounds the size up to a whole cylinder of the geometry it writes — 8 MiB of data comes out as a disk of 8390656 bytes — and what is past the data reads as zeroes.
- **A differencing image is refused.** It holds only what changed from another disk, and reading one means reading its parent, which is a file this cannot reach.

## What a QCOW2 image is, of what matters to read one

- **Two levels of tables.** The header says how large a cluster is (`cluster_bits`, 512 bytes to 2 MiB), and the disk is that many bytes at a time. The first level has an entry for each table of the second, and each of those has an entry for each cluster; both hold byte offsets in their bits 9 to 55, so an offset is always a whole number of clusters. An entry of zero is a part of the disk nothing has been written to, and reads as zeroes.
- **An entry's lowest bit, in version 3, means the cluster reads as zeroes**, whatever else the entry says. Version 2 has no such bit, so it is honoured only for version 3.
- **A compressed cluster's entry is shaped by the cluster size.** With `x = 62 - (cluster_bits - 8)`, its bits 0 to x-1 are a byte offset — aligned to nothing — and bits x to 61 are how many 512-byte sectors follow the one that offset is in. Those sectors are not the length of the compressed data: the last of them holds whatever came after it, and decompressing stops when a cluster has come out.

  That difference is where a reader goes wrong. Deflate does not mind, as it stops at the stream's end; **Zstandard does**, because decompressing a buffer expects it to be exactly one frame, so the frame's own length is read first (`find_frame_compressed_size`) and only that is decompressed. hivepack's first attempt passed the whole sector range and failed on every zstd image.
- **Compression is raw deflate, or Zstandard.** Deflate with no zlib header around it (`-15` window bits), which is what every image before the field had; version 3 may say Zstandard instead, in a byte after the header, and hivepack reads those only in a build with its own `zstd` feature — otherwise the image is refused rather than read as holes.
- **Refcounts are not read.** They say which clusters are free, which only writing needs, so an image whose refcount table is marked dirty is read as it is. An image marked *corrupt* is refused: that bit says the last writer left it wrong.
- **Snapshots are not read.** Each is another first-level table in the same file; what is read is the disk as it is now.
- **What is refused, and why.** Each of these would otherwise be read as a disk of holes, which is worse than an error: an image with **another behind it** (a backing file, and a differencing VHD is the same thing — `Unsupported::Backing`), one whose **data is in a file of its own**, one that is **encrypted**, one marked **corrupt**, one using **subclusters** (extended L2 entries, QEMU 5.2), one needing a feature **nothing here knows**, and Zstandard in a build without it.
- **Nothing is cached.** An entry of the second level is eight bytes, read when it is wanted. What reads a disk image reads it in order, and the `Disk` underneath may cache as it likes.

## What a VMDK is, of what matters to read one

- **A VMDK is one file or several**, which is what sets it apart from every other container here. A **descriptor** of plain text says what the disk is made of, and the **extents** named in it hold it. `monolithicSparse` and the `streamOptimized` stream an OVA carries keep the descriptor inside the one file; `monolithicFlat` and the two kinds that cut a disk into 2 GiB pieces are a descriptor naming files beside it. So `Vmdk::open`, which is handed a reader, reads the first kind and refuses the second with `Unsupported::Beside`, and `Vmdk::beside`, which is handed a path, reads both.
- **A name in a descriptor is read as a name, never as a path.** A descriptor is text in a file that was opened, and it names the files to open next: `../`, a folder of its own, or an absolute path is refused (`Error::VmdkElsewhere`), so that opening an image cannot be made to read a file somewhere else. Every descriptor any tool writes names a plain file beside itself.
- **Extents are joined in the order the descriptor names them.** A `FLAT` extent is the disk as it is at an offset into its file; a `SPARSE` one is read through its own header, which says how long the disk it holds is — the descriptor's number is not what is believed, as that is what QEMU reads too; a `ZERO` extent holds nothing at all and reads as zeroes. A flat file **shorter than its extent** reads as zeroes past its end, which is a disk whose end was never written: ESXi writes such files thin.
- **A sparse extent is a header, a directory of grain tables, and grains.** Everything is little-endian and counted in sectors of 512 bytes. A grain is 128 sectors (64 KiB) in every image anything writes; a grain table holds 512 entries, each four bytes, saying in sectors where that grain is. An entry of **0** is a grain nothing was written to and an entry of **1** is one written as zeroes — the format has the second so that a stream need not carry them — and both read as zeroes. A directory entry of 0 is a whole table's worth of the same.
- **A stream of compressed grains says its directory is at the file's end.** `gdOffset` is `0xFFFFFFFFFFFFFFFF`, because what wrote the stream in one pass could not know where the directory would land. The real header is in a **footer** in the last three sectors: a marker saying a footer follows, the header itself, and a marker saying the stream ends. hivepack reads the footer when the header says so, and refuses a footer that says the same thing again rather than looking at the end for ever. `qemu-img` writes the directory in place instead, which both shapes being read is checked on.
- **A compressed grain is behind a marker of its own**, twelve bytes saying which sector of the disk the grain holds and how many bytes it takes, and the bytes after it are deflate **with a zlib header** — the specification names deflate, and what VMware and QEMU write carries the wrapper, so it is inflated with 15 window bits where QCOW2's clusters take -15. Nothing is cached: a grain is decompressed whole, each time, as a QCOW2 cluster is.
- **A header of no capacity is a descriptor with a header in front of it**, which is what a tool that cuts a disk into pieces writes: there are no grains in it, and the files it names hold the disk.
- **What is refused, and why.** An image holding only **what changed from another** (`parentCID` is not `ffffffff`, or there is a parent's name: `Unsupported::Backing`) — a `monolithicSparse` file is what QEMU writes for one, so its own descriptor is read for this even when `open` needs nothing else from it. **SESPARSE**, VMware's newest kind, keeps its tables somewhere else again (`Unsupported::Feature`), as does a version past 3 or a compression that is not deflate. A grain size the format does not have, a table that is not on the file, a descriptor naming no extent or more than 1024 of them: `Error::VmdkSays`.
- **The redundant grain directory is not read.** A sparse extent may carry a second copy of its directory and tables, which VMware keeps for repair; QEMU does not read it either, and what a reader needs is in the first.

## What a VHDX is, of what matters to read one

- **Everything is little-endian**, where VHD, its elder, was big-endian throughout, and each header and region table carries a **CRC-32C** — Castagnoli's, not the CRC-32 a GUID partition table uses, so `image` has a small one of its own (`crc32c.rs`, checked against the published values).
- **Two headers, at 64 KiB and 128 KiB.** Each holds a sequence number, and the one that counts is whichever passes its own CRC-32C with the greater number: that is how whatever wrote the file last left it.
- **Two region tables, at 192 KiB and 256 KiB**, each naming where the parts of the file are by GUID. Two matter: the table of blocks, and the metadata. A region the image marks as needed and this does not know is refused, since what is in it may be what the disk is.
- **The metadata says what the disk is**: how long it is, how large a block is, and **how many bytes a sector is** — 512 or 4096. No other container here says the last of these, and a master boot record cannot: this is what `partitions_in` was for.

  Every one of the five items the specification defines is marked as needed, including the two nothing here wants (what tells a disk apart, and the size its hardware writes in). That flag says a reader which cannot make sense of an item must not read the disk, and a reader is meant to know these five — so they are named and passed over, and only an item that is both unknown **and** needed is a reason to refuse. Taking the flag at face value refused every image `qemu-img` writes, which is how this was found.
- **The table of blocks is not only blocks.** Its entries come in runs of `chunk = 2^23 × sector ÷ block`, each run followed by one entry that is a bitmap rather than a block of the disk, so the entry for a block is at `block + block ÷ chunk`. An entry's low three bits say whether the block is there; its upper bits hold where it is, **counted in megabytes**. A block that was never written, or that the image says is zeroes, or that has been trimmed, reads as zeroes.
- **A log that was written and never applied is refused.** What its entries say belongs in the tables, and putting it there is writing; a reader that passed over it would answer with what the disk held before.
- **An image with another behind it is refused**, as a differencing VHD and a QCOW2 image with a backing file are (`Unsupported::Backing`). Its blocks are marked as only partly present, and what is missing is in the image it came from.

## How it is checked

`crates/hivepack/tests/image_partitions.rs`, for the disk and its tables, and one file for each container beside it: `image_vhd.rs`, `image_qcow2.rs`, `image_vhdx.rs`, `image_vmdk.rs`.

- **Tables built byte by byte**, with their CRC-32s computed as a tool computes them: a master boot record of two partitions; an extended partition holding two logical ones, numbered 5 and 6; a chain that leads back into itself; a GUID partition table whose names are UTF-16 and not all ASCII; a damaged primary header, where the copy at the end gives the same answer; both copies damaged; entries that fail their check; a partition past the end of the disk; a protective record with no table behind it; a GUID partition table counted in 4096-byte sectors; a master boot record read both as every tool reads one and in the sectors `partitions_in` is told, with the sector sizes no disk has refused; and files that have no table at all.
- **Tables util-linux wrote**, where `sfdisk` is installed: the same two layouts, in a 16 MiB image, read back and compared with what was asked for — the partitions' places, sizes, types, names and bootable flags. Where it is not installed, or cannot be run at all — CI's 32-bit container answers `ENOSYS` to starting a process — the test says so and passes; the tables built by hand are what CI checks everywhere.
- **VHD against `qemu-img`**, where it can be run: a disk with data and holes, as fixed and as growing, a disk of nothing but holes, and a disk full of data, each converted to VHD by `qemu-img` and then read twice — once by `qemu-img convert -O raw` and once by hivepack — with the two compared byte for byte, lengths included, and with what went in checked to be at the front of what comes out and the rounding's own bytes to be zeroes. And the partitions of a card's image read through a VHD, which is the layering working.
- **VHDX against `qemu-img`**, where it can be run: a disk with data and holes, one of nothing but holes, one full of data, and block sizes of 1, 2 and 8 MiB — each read by `qemu-img convert -O raw` and by hivepack and compared byte for byte. And the sector size: `qemu-img` writes 512 and its vhdx driver has no option for anything else, so the image it wrote is read, then the one item is changed to 4096 in a copy (the metadata table carries no checksum, so nothing else has to be put right) and read again — the same partition comes out eight times further in, which is what says the field is read and not assumed.
- **QCOW2 against `qemu-img`**, where it can be run: a disk with data and holes, one of nothing but holes, one full of data, clusters compressed with zlib and with Zstandard, and cluster sizes of 512 bytes, 4 KiB and 2 MiB — each read by `qemu-img convert -O raw` and by hivepack and compared byte for byte, with the disk's own bytes unchanged (QCOW2 keeps the size it was asked for, where a VHD rounds). A card's partitions read through a QCOW2 image. And the images `qemu-img` makes that are refused: one with a backing file, and one whose data is in a file of its own.
- **VMDK against `qemu-img`**, where it can be run: a disk with data and holes, one of nothing but holes, one full of data, and grains written as zeroes in the tables (`zeroed_grain=on`) — each in **all five kinds `qemu-img` writes** (`monolithicSparse`, `monolithicFlat`, `twoGbMaxExtentSparse`, `twoGbMaxExtentFlat`, `streamOptimized`), read by `qemu-img convert -O raw` and by hivepack and compared byte for byte, with the disk's own bytes unchanged (VMDK rounds nothing up past a sector). A card's partitions read through a VMDK. The image `qemu-img` makes that is refused, which is one holding only what changed from another. And the footer: `qemu-img` writes the grain directory in place, so the stream it wrote is turned into the shape VMware writes — the header saying the directory is at the end, and a footer there holding the header as it was — and read again, the same grains found the other way, with a stream whose footer is missing and one whose footer says the same as the header both refused.
- **VMDK descriptors written by hand**, so that what `qemu-img` cannot write is checked, and so that CI checks the reader where `qemu-img` is not installed: a disk in two extents, flat and sparse, joined in order; a `ZERO` extent and a flat file shorter than its extent, both reading as zeroes; names that are paths, each refused; a descriptor of its own handed to `Vmdk::open`, with and without a header in front of it; a `SESPARSE` extent; a version the format has not reached; and the grain sizes, entry counts and directory offsets a sparse extent cannot have.
- **QCOW2 images built byte by byte**: an image whose clusters are written, missing and marked as zeroes; a cluster size the format does not have; a first level too small for the disk; an encrypted image; one marked corrupt; and an incompatible feature bit nothing knows.
- **VHD images built byte by byte**, so that CI checks the reader where `qemu-img` is not installed: an image that grows, read in pieces that do not line up with its blocks; the footer at the start read where the one at the end is ruined; a block whose bitmap is all zeroes; a footer whose size and geometry disagree; and the four ways one is refused — a file that is not a VHD, a dynamic header that fails its checksum, a differencing image, and a block size that is not a power of two.

## What a reader should know

- A GUID partition table's entry size is not always 128 bytes: the specification allows more, and the array is read in entries of the size the header gives.
- A name is UTF-16, little-endian, to the first NUL. An empty name is none, not an empty string.
- `Partition::id` is a GUID partition table's unique GUID for the partition, written as every system writes one (the first three fields with their bytes the other way about, as they are on the disk). A master boot record has none.
- `bootable` is an entry's active flag in a master boot record, and the legacy BIOS bootable attribute (bit 2) in a GUID partition table. Neither says anything about what boots on a system that uses the other.

### VHD

- **Against `qemu-img`, byte for byte.** Four blocks of data whose bytes are the same nowhere, the second and fourth of them zeroes so that a tool leaves them unwritten, converted to a dynamic image and to a fixed one, and read back whole in runs of 512 bytes, of a block, of a block and a sector, and of 3587 bytes, so that reads landing on a block's start, on its end and across it are all made. The same data read out of the image by `qemu-img convert -O raw` is compared too, so that both agree about what is in it.
- **The partitions of a VHD are the partitions of the disk that went into it**: a GPT written by `sfdisk` into a raw image, converted to a VHD, read through `Vhd` and compared with what was read from the raw.
- **Images built byte by byte**, with their checksums as a tool computes them, so that CI checks the reader where `qemu-img` is not installed: blocks written and unwritten in turn, a read that crosses from one into the other, a fixed image, a footer at the end that does not hold (where the copy at the start is read), a differencing image, a dynamic header whose checksum fails, and a disk type nothing has.
- Where `qemu-img` or `sfdisk` is not installed, those tests say so and pass.
