# Porting liblzma

`hivepack::xz` is a port of liblzma, the library of [XZ Utils](https://tukaani.org/xz/), to safe Rust. It encodes `.xz` and `.lzma` files and raw LZMA1 and LZMA2 streams, with the delta and BCJ filters before LZMA where the format has them, and decodes those and `.lz` files (liblzma has no `.lz` encoder); tar files use it for `.tar.xz`, and ZIP archives for their methods 14 (LZMA) and 95 (XZ). The goal is the one [porting.md](porting.md) sets for zstd: the same results as liblzma, at the same speed.

The decoders came first, then the encoders, then the delta and BCJ filters, then the multithreaded encoder and decoder. What is left is in [Not ported, for now](#not-ported-for-now).

## The version

The port follows XZ Utils **5.8.4** (9 September 2026), the current release as of October 2026: `xz-5.8.4.tar.gz` from its GitHub releases, SHA-256 `0014c7886930454fe8bd4228665b51af55eeae560ea135c9c4cd33f55b2591d9`, whose signature by Lasse Collin (key `3690C240CE51B4670D30AD1C38EE757D69184620`) was checked, and whose `src/liblzma` and `tests/files` are those of the git tag `v5.8.4`. `hivepack::xz::UPSTREAM_VERSION` names it, `hivepack::xz::version_number()` gives what `lzma_version_number()` gives, `50080042`, and `version_string()` gives `"5.8.4"`.

## What following the official code means

The rules of [porting.md](porting.md):

- **The same layout.** Each file of liblzma becomes a module named after it: `common/stream_decoder.c` becomes `crates/hivepack/src/xz/stream_decoder.rs`, `lzma/lzma_decoder.c` becomes `lzma_decoder.rs`, `lz/lz_decoder.c` becomes `lz_decoder.rs`, `lz/lz_encoder.c` and its match finders (`lz_encoder_mf.c`) `lz_encoder.rs`, `lzma/lzma_encoder.c` with its two ways of choosing symbols (`lzma_encoder_optimum_fast.c` and `lzma_encoder_optimum_normal.c`) `lzma_encoder.rs`, `delta/`'s common, decoder and encoder files `delta.rs`, `common/stream_encoder_mt.c`, `stream_decoder_mt.c` and `outqueue.c` `stream_encoder_mt.rs`, `stream_decoder_mt.rs` and `outqueue.rs`. The BCJ filters keep their folder: `simple/x86.c` becomes `simple/x86.rs`, and so on for each architecture, and `simple_coder.c`, `simple_decoder.c` and `simple_encoder.c` are `simple/mod.rs`. The headers' constants and inline functions are beside the code that uses them (`lzma_common.rs`, `range_decoder.rs`, `range_encoder.rs`), and `common.c`'s `lzma_code()` and the coders' common parts are in `common.rs`.
- **The same names**, in snake case, with the C name in every doc comment. An `lzma_stream` and its coder are one type, `Stream`, made by the function that initialises it: `lzma_stream_decoder()` becomes `Stream::stream_decoder`, `lzma_easy_encoder()` becomes `Stream::easy_encoder`, `lzma_code()` becomes `Stream::code`, `lzma_stream_encoder_mt()` and `lzma_stream_decoder_mt()` with their `lzma_mt` become `Stream::stream_encoder_mt` and `Stream::stream_decoder_mt` with an `MtOptions`; the single-call functions keep their names (`easy_buffer_encode`, `stream_buffer_encode`, `raw_buffer_encode`, `bcj_x86_encode` and the other BCJ functions of liblzma 5.8).
- **The same algorithms and constants.** The CRC tables and the encoder's price table are computed while compiling, as liblzma's `crc32_tablegen.c`, `crc64_tablegen.c` and `price_tablegen.c` compute the tables it keeps as source, and tests check them against their definitions, check values and liblzma's table.
- **The same results.** A call returns liblzma's code, as `Result<Status, Error>` with the same numbers (`Status::number`, `Error::number`), and reads and writes what liblzma reads and writes: the encoders write liblzma's bytes, whatever pieces the input and output come in. The memory usage and limits are liblzma's numbers too.
- **Differences are marked** with a comment starting `Differs from liblzma`.

liblzma's coders are a chain of `lzma_next_coder` structures, each with function pointers to its code, end, check and memory functions; the port's are boxes of a trait, `NextCoder`, whose methods have liblzma's defaults (none for the check, `LZMA_PROG_ERROR` for the memory functions). A filter's coder holds the next one, as in liblzma: the decoders of a chain in its order, each filtering what the next one decodes, and the encoders in reverse, so that LZMA, last in the chain, reads from the filters before it, the first of which reads the input. They are made in liblzma's order too, so that when several filters are refused, the error is the one liblzma gives. `lzma_code()`'s rules are kept as they are: the actions each coder accepts (the `.xz` encoder all five, the raw encoder `LZMA_SYNC_FLUSH` too, the `.lzma` encoder and the decoders only `LZMA_RUN` and `LZMA_FINISH`), the input that must not change after `LZMA_FINISH`, `LZMA_BUF_ERROR` on the second call that can do nothing, and `LZMA_PROG_ERROR` from then on after an error. The stream holds the totals; the caller's input and output come with each call, as an `InBuffer` and an `OutBuffer`, a slice and a position, as in `hivepack::deflate`, `hivepack::zstd` and `hivepack::bzip2`.

The LZMA decoder keeps liblzma's two modes. The resumable one, which liblzma writes as a `switch` whose `case` labels sit inside the code of a symbol so that it can stop wherever the input or the output runs out and start there again, is a `match` on the same sequence values. The fast one, the Non-resumable mode, decodes whole symbols while there are 20 bytes of input at least and room in the dictionary, with liblzma's unrolled bittrees and its branchless bit decoding: on x86-64 liblzma has this in inline assembly, elsewhere in C (`rc_c_bit`); the port has the C. The probabilities are one array in the order of `lzma_lzma1_decoder`'s fields, so that a bittree is an index into it, as liblzma's `probs` is a pointer.

The LZMA encoder is liblzma's too: the match finders (two hash chains and three binary trees), the range encoder that queues up to 53 bits and writes them out as the output space allows, the fast mode's heuristics, and the normal mode's search for the cheapest way through up to 4,096 positions, with liblzma's price tables. Its probabilities are the decoder's array, and the range encoder queues indices into it where liblzma queues pointers.

The other differences:

- **The dictionary's buffer grows as it is written.** liblzma allocates the dictionary, up to 4 GiB, when the decoder starts, and leaves it as allocated; the port reserves the same memory then (failing to is `LZMA_MEM_ERROR`, as a `NULL` from `lzma_alloc()` is), and zeroes it up to where each call may write. liblzma reads only what it wrote, so nothing differs.
- **The Index hash** is liblzma's: SHA-256 of each Block's two sizes. liblzma hashes them as they are in memory, the port in little-endian order, on the Blocks' side and the Records' alike, so the comparison is the same.
- **The memory usage** counts liblzma's structures by their sizes on 64-bit machines (`sizeof(lzma_lzma1_decoder)`, 28,352 bytes, `sizeof(lzma_lzma1_encoder)`, 249,552 bytes, and the others), on every machine: the numbers are liblzma's on x86-64 and arm64, and the port's own structures are not those.
- **What C needs and Rust does not:** custom allocators, `lzma_end()` (dropping the stream), and the checks of null pointers and reserved members. A buffer whose `pos` is past its end fails with `LZMA_PROG_ERROR`.
- **A stream is `Send`**, so that it can be moved to another thread, as an `lzma_stream` can: `NextCoder` asks it of every coder.
- **CRC32 and CRC64** are computed slice-by-eight from their tables, as liblzma's generic code does. With `unsafe-fast`, on x86-64, they are folded with the processor's carry-less multiplication where there are 64 bytes or more, as liblzma's CLMUL version does (`src/clmul.rs`, shared with `deflate`; see [unsafe.md](unsafe.md)): CRC64 then costs 4% less of decoding a `.xz` file. liblzma's ARM64 and LoongArch versions are not ported; all give the same values.
- **The encoder's buffers grow as they are written.** liblzma allocates the history buffer and the binary trees of the match finder at their full size and leaves them uninitialised (only the hash table is zeroed); the port reserves the same memory, asks for the hash table zeroed (as liblzma asks `calloc()`, so that the system zeroes a big one's pages only as they are touched), and lets the buffer and the trees grow as the data and the positions reach them. The match finders read only what they wrote, and the normalization that liblzma does about every 4 GiB, over all the hash table and the trees, is done over what exists. Safe Rust has no zeroed allocation that can fail, so where the hash table (at most 64 MiB) cannot be had the process aborts, where liblzma returns `LZMA_MEM_ERROR`; the bigger buffer and trees are reserved before it with that check. The normal mode's 4,096 `opts[]`, which liblzma leaves uninitialised, are made only for that mode. (Zeroing the hash table at once had made a 1 KB input take 9.6 ms at preset 9, where liblzma takes 77 µs; now 1 KB inputs take what liblzma takes at every preset.)
- **Distance slots are computed** (`get_dist_slot`), as liblzma does when built with `HAVE_SMALL`, where its default build looks them up in an 8 KiB table, `lzma_fastpos`; a test checks that they are the table's.
- **`lzma_memcmplen` compares within its limit.** liblzma compares words and may read up to `LZMA_MEMCMPLEN_EXTRA` bytes past the limit (16 at most), which it ignores; the port compares eight bytes at a time and stops at the limit.
- **Encoders are kept between Blocks, in part.** `lzma_next_coder_init()` lets liblzma's init functions reuse a coder of the same kind in all of a chain. The port keeps the LZ encoder, with the LZMA or LZMA2 encoder and the match finder's memory, as `raw_encoder_reinit()`; delta and the BCJ filters, which are small, are made anew. As in liblzma, the buffer and the trees are kept while their sizes stay, and the hash table is zeroed for each Block.
- **The Index of the encoders is a list.** liblzma's `lzma_index` keeps Streams and groups of Records in trees, to find Blocks by their offsets; the `.xz` encoder only appends Records and writes them out in order.
- **Filter options say their type.** liblzma's `lzma_filter` points to options that its Filter ID says how to read, whatever they are; the port's `FilterOptions` says what they are, and options of another filter's type are refused: with `LZMA_OPTIONS_ERROR` for delta and BCJ, as invalid ones are, and with `LZMA_PROG_ERROR` for LZMA, as none are (liblzma's encoders give that for none; its decoders do not check).
- **Threads.** liblzma's threads, mutexes and condition variables (`mythread.h`) are `std::thread`, `Mutex` and `Condvar`, each mutex holding what liblzma's protects: the coder's its error, its free workers, its progress and the output queue; a worker's its state and input. Two hand-overs differ, as safe Rust has them: liblzma's main thread writes a Block's input into the worker's buffer while the worker reads the part before it, where here it appends it to a buffer the worker exchanges with its own, or empties into it; and a worker takes its output buffer from the queue while it writes and gives it back when the Block is done, where liblzma's stays in the queue (its main thread reads only finished Blocks either way). The decoder hands the input over the same way, and its main thread does read what a worker has written so far, from the worker of the oldest Block: where liblzma's worker updates `outbuf->pos`, under the coder's mutex, the port's moves what it has written to the queue, the whole buffer the first time and a copy of the rest after that. The buffers grow as they are written, and the Block encoder or decoder is called again when it has filled what there is, as with a buffer of the full size. The memory usage counts liblzma's structures as glibc's POSIX threads make them on x86-64 Linux (`sizeof(lzma_stream_coder)` 568, `sizeof(worker_thread)` 544), on every machine; `tests/oracle.rs` compares them with liblzma's live only there.
- **`LZMA_UNSUPPORTED_CHECK` as an error.** Making a `.xz` encoder with a check this build cannot compute fails with it; it is `Error::UnsupportedCheck`, where `Stream::code` gives it as `Status::UnsupportedCheck`.

### What liblzma does, kept

- **A known size with an end marker, split.** liblzma decodes `.lzma` files that have their size in the header and an end of payload marker after the data, which some encoders write (XZ Utils' `good-known_size-with_eopm.lzma`). When the input given to a call ends inside that marker, the next call refuses it with `LZMA_DATA_ERROR`: whether the marker may come is a local variable of `lzma_decode()`, set when the size is reached, and forgotten when the call returns in the middle of the marker. `xz -dc` 5.8.3 fails so on valid files whose marker crosses its 8 KiB reads ("Compressed data is corrupt"), and decodes them when read whole. The port gives the same results, call by call, so as not to differ from liblzma; the decoder of LZMA1 with LZMA1EXT and a known size is affected too. Reported as [tukaani-project/xz#260](https://github.com/tukaani-project/xz/issues/260), with a one-line fix; the port will follow liblzma's fix when it is released.
- **The check before the Stream Header.** `lzma_get_check()` on an `.xz` decoder that has not read its Stream Header returns `stream_flags.check`, which liblzma has not set yet: whatever its allocation held. The port returns `LZMA_CHECK_NONE`, and the oracle (below) allocates with `calloc` to give the same.

## How it is shown

The reference is liblzma 5.8.4 itself, through `tools/xz-oracle`, a small C program built from the release tarball by `scripts/testdata.py`, with the decoders and encoders of LZMA1, LZMA2, delta and the eight BCJ filters, the `.lz` decoder, and the three checks; and, for the fuzzer and the benchmark, built from the sources bundled in `liblzma-sys` 0.4.9 (its `static` feature, so that a system liblzma, which may be another version, is never used) and called through the `liblzma` crate.

- **`tests/oracle.rs`** compares every call: a request is a decoder and a list of steps, calls with some input and output space and an action, memory limits set, and queries of the memory usage, the limit and the check; the port must answer each as liblzma does, with the result and the bytes read and written, then the totals and a hash of the output. The streams come from liblzma's encoders: `.xz` at presets 0 to 9 and extreme, with no check, CRC32, CRC64 and SHA-256; `.lzma`, with the size in its header or not, right or wrong; raw LZMA1 and LZMA2, decoded with the encoder's dictionary, a smaller one, or none, and now and then a preset dictionary; and `.lz` members, version 0 and 1, made from raw LZMA1. Some are damaged, cut short, concatenated with Stream Padding, valid or not, or followed by more, and some `.xz` Streams have a check ID the build does not support. XZ Utils' own test files, `tests/files`, are decoded too, by every decoder they suit. Filter chains, `.xz` and raw, have one to three delta and BCJ filters before LZMA2 or LZMA1: delta distances from 1 to 256, BCJ start offsets of 0, none, in alignment, near 4 GiB (where positions wrap around) and, refused, out of it; the input has the instructions each BCJ filter converts (x86 `CALL` and `JMP`, `BL` of PowerPC, ARM, ARM-Thumb and ARM64, SPARC `CALL`, ARM64 `ADRP`, RISC-V `JAL` and `AUIPC` pairs) among other bytes. Chains liblzma refuses are tried too: LZMA not last, five filters, a BCJ or delta filter last, no or invalid options, Filter IDs it does not have. Each is decoded in random pieces, with the flags of the decoders, low memory limits that are reached and then raised, actions the decoders refuse, and calls after the end. 1,281 requests are compared with liblzma where the oracle is built (Linux and macOS in CI), with every return code but `LZMA_MEM_ERROR`; `testdata/oracle/xz.txt` replays 1,156 earlier answers everywhere else, including Windows, 32-bit and big-endian machines. Before the first commit, the same comparison ran with 450 seeds, about 550,000 requests, with overflow checks and debug assertions on, and and with 300 more once the filters were in: no difference and no panic.
- **`tests/oracle.rs`** compares the encoders call by call too, and their output by its hash: the `.xz` encoder of a preset (0 to 9 and extreme) and of an LZMA2 chain, the `.lzma` encoder and the raw encoders of LZMA1, LZMA1EXT and LZMA2, with the options of the presets changed at random: dictionary sizes, lc, lp and pb, the fast and normal modes, `nice_len`, each of the five match finders, the search depth, the end marker of LZMA1EXT, and preset dictionaries, some of them refused (as are Filter IDs liblzma does not have, and checks out of range or not built). Each input, from none to 3.5 MB, is given in random pieces with random room for output, with `LZMA_SYNC_FLUSH`, `LZMA_FULL_FLUSH` and `LZMA_FULL_BARRIER` where the encoder takes them (and given again until done), actions it refuses, memory limits and queries; the inputs over 1 MB slide the window of small dictionaries and fill LZMA2 chunks of 2 MiB. `lzma_easy_buffer_encode()`, `lzma_stream_buffer_encode()` and `lzma_raw_buffer_encode()` are given output space that is enough, short, or tiny, so that incompressible data goes into LZMA2's uncompressed chunks and too little space fails; and the memory usage of encoders and presets, and `lzma_stream_buffer_bound()`, are compared too. The `.xz` and raw encoders, the single-call ones and the memory usage have filter chains as the decoders do, and the big inputs a third of the time; `lzma_bcj_x86_encode()`, `lzma_bcj_arm64_encode()`, `lzma_bcj_riscv_encode()` and their decoders, with any start offset. 897 requests are compared with liblzma, and `testdata/oracle/xz-encode.txt` replays 697 earlier answers elsewhere. Before the first commit, 150 seeds of the encoders' comparison ran with overflow checks and debug assertions on, and each match finder encoded 4.4 GB in the same pieces as liblzma, through the normalization of its positions that comes after 4 GiB: the same output, no panic.
- **The multithreaded encoder** writes liblzma's Streams, but how much each call reads and writes depends on when its threads finish, in liblzma as here. So `tests/oracle.rs` gives liblzma's and the port's encoders the same steps, the input in pieces with `LZMA_RUN` and room for all the output (with less, a call may return before it has read all its input), `LZMA_FULL_FLUSH` and `LZMA_FULL_BARRIER`, and `LZMA_FINISH`, the last three with random room and made again until they are done; then compares the result of the last call, the totals and the Stream, or the error. One to four threads (and options refused: none, 16,385, flags), Blocks from one byte to the chain's own size and up to 5 MB of input in Blocks of 256 KiB to 1 MiB, presets and chains with delta and BCJ filters, every check: 154 encodings and 50 memory usages, all as liblzma's, with 170 recorded. The oracle builds liblzma with POSIX threads. `tests/mt.rs` checks what cannot be compared: a timeout that makes calls return before they are done, with the same Stream; the progress, which grows to the totals; sixteen threads with Blocks of 1,000 bytes; and streams dropped while their threads work.
- **The multithreaded decoder** gives liblzma's output, and its end, which also do not depend on the threads, where the bytes read after an error, and what comes first with `LZMA_FAIL_FAST`, do. So `tests/oracle.rs` gives both decoders the same steps, pieces with `LZMA_RUN` and then `LZMA_FINISH` until it ends, with random room, and compares the output, the last result, the number of `LZMA_NO_CHECK`, `LZMA_UNSUPPORTED_CHECK` and `LZMA_GET_CHECK` results, the total output, and after the end of a Stream the bytes read. One thing depends on the threads in liblzma too: when the coder after a BCJ coder fails, `simple_code()` returns with what it had not filtered left in the output, and how much that is depends on how the input came to the worker, so the same damaged Stream gave liblzma four different outputs in 60 runs. For a Stream with BCJ filters that fails, only the result is compared (and in the port, whose worker writes in steps, up to about 100 of those unfiltered bytes may stay in the coder, where liblzma's would mostly come out). One to four threads (and refused counts and flags), memory limits that send Blocks to the direct mode or stop the decoder, every flag; the Streams of the threaded and the single-threaded encoder (with and without the sizes that threads need), with delta and BCJ filters, concatenated with Stream Padding, damaged, cut short, followed by more, and XZ Utils' `.xz` test files. 371 requests are compared with liblzma, and `testdata/oracle/xz-mt.txt` replays 298 answers elsewhere; before the first commit, 200 seeds ran with overflow checks and debug assertions on, with no difference and no panic. `tests/mt.rs` checks a timeout, the progress, sixteen threads with Blocks of 1,000 bytes, decoders dropped while their threads work or wait for input, input that stops (`LZMA_BUF_ERROR`, after all the output possible), memory limits reached and raised, and `LZMA_FAIL_FAST`.
- **`tests/files.rs`** decodes XZ Utils' test files as its `tests/test_files.sh` does with `xz -dc`: every `good-` file decodes, those with delta and BCJ filters among them, every `bad-` and `unsupported-` file fails, and each gives the same results decoded at once and a byte at a time (but for the end marker above).
- **Unit tests** check the CRC tables against their polynomials, CRC32, CRC64 and SHA-256 against their check values, the price table against liblzma's, and the distance slots against `lzma_fastpos`.
- **`fuzz/fuzz_targets/xz.rs`** decodes the fuzzer's input with each decoder, its flags, memory limit and options from the input, in pieces, against liblzma through the `liblzma` crate: every call must give the same result, bytes read and written, and output (see [fuzz/README.md](../fuzz/README.md)). **`xz_encode.rs`** does the same with each encoder, its preset, check and options from the input, with flushes. Both put up to three delta and BCJ filters before raw LZMA and the `.xz` encoder's LZMA2, from their properties. `xz_encode.rs` drives the multithreaded encoders as `tests/oracle.rs` does and compares their Streams, and `xz.rs` the multithreaded decoders, without flags, for which the `liblzma` crate has no setter.

## The speed target

At least 0.95× liblzma's speed, as for zstd, zlib and bzip2, measured with `tools/xz-bench` on the Silesia corpus (`python3 scripts/testdata.py fetch --group bench` fetches it):

```sh
cargo run --release -p xz-bench -- [--presets 0,6,9] [--check none|crc32|crc64|sha256] [--compress] target/testdata/silesia
```

Each run decodes a whole `.xz` Stream that liblzma wrote, or with `--compress` encodes the file at the preset, in one call, on a new decoder or encoder, with room for all the output. With `--compress`, the tool also checks that the port's Streams are liblzma's, byte for byte.

### Where it stands

AMD Ryzen 9 9950X (x86-64, Linux), October 2026, the 12 Silesia files with CRC64. Compression at presets 0, 3, 6 and 9, best of two rounds taken in turn:

| | Mean | Range | At 0.95× or more |
|---|---|---|---|
| Compression | 1.02× liblzma | 0.93–1.18× | 46 of 48 |

Every Stream was liblzma's, byte for byte. By preset, the means are 1.03×, 1.04×, 0.99× and 1.01×; the two below 0.95× are `dickens` and `mr` at preset 9 (0.94× and 0.93×). The encoder was there as first ported.

Decompression at presets 0, 6 and 9, best of three rounds, November 2026. liblzma is built as `liblzma-sys` builds it, which on x86-64 with GCC or Clang decodes its range coder's bittrees, matched literals, reverse bittrees and direct bits in inline assembly (`LZMA_RANGE_DECODER_CONFIG` 0x1F0); on other machines, arm64 among them, liblzma has C there. Both are measured, the C one by building `liblzma-sys` with `CFLAGS=-DLZMA_RANGE_DECODER_CONFIG=0`:

| | Mean | Range | At 0.95× or more |
|---|---|---|---|
| Against liblzma with its x86-64 assembly | 0.94× | 0.89–1.03× | 11 of 36 |
| Against liblzma's C | 1.44× | 1.23–1.69× | 36 of 36 |

By preset, against the assembly: 0.93×, 0.95× and 0.95×. So the port is well past liblzma's speed where liblzma is C, and at it on x86-64, where it is assembly, on average just under the target. As first ported, with the resumable mode only, as liblzma has with `HAVE_SMALL`, the port was at 0.60–0.82×; the Non-resumable mode brought it to 0.81× (0.74–0.89×; 1.18× liblzma's C), and decoding its bittrees as the assembly does to the numbers above:

- **The bits of a bittree, a literal's above all, as liblzma's assembly decodes them** (`bittree_fast!`, `matched8!` in `lzma_decoder.rs`, the Non-resumable mode only). A node's two children's probabilities are read before its bit is known, and the bit picks one (`std::hint::select_unpredictable`, a `cmov`), so that reading them is not on the way from one bit to the next: that way is then the multiplication and the comparison, as in the assembly. For a literal after a match the two indices the next bit may take are made from the match byte's bit as both outcomes would make them. Each tree is taken once as an array of its size (a literal coder's 0x300, a length's 8 or 256, a slot's 64), its bounds checked there, and every index into it is masked to it, so the compiler leaves out the check of each read. The bits and the probabilities written are the C's. Plain literals: 0.81× to 0.84×; literals after a match: to 0.90× (`x-ray` 0.79× to 0.99×, `mr` 0.81× to 0.94×); lengths and slots: to 0.94×. Reading both children with a bounds check on each, as tried before, gained nothing; and masking every index of the whole array of probabilities, rounded up to 16,384, made it 2–3% slower.

Bounds checks left cost little more: the input's, once per byte of it, and the dictionary's. arm64 is not measured yet.

### The multithreaded encoder

`--compress --threads N` times the multithreaded encoders, in Blocks of the preset's size (three times its dictionary, at least 1 MiB), and checks that the Streams are the same. Silesia at presets 0 and 3, on a machine that other work was using too: with 4 threads 1.01× liblzma on average (0.83–1.11×, 22 of 24 at 0.95× or more; the two below are noise, `x-ray` at preset 3, a single Block, being 0.97× at best of ten rounds), with 16 threads 1.01× (0.96–1.09×, 24 of 24).

Very small Blocks cost about what they cost liblzma, as both keep a Block's encoder for the next one: 20,000 bytes in Blocks of 1 byte take 0.11 s in one thread against liblzma's 0.10 s, and 0.03 s in four as liblzma does; in Blocks of 100 or 4,096 bytes about 1.2× as long. 20,000 bytes in one Block take 0.33 ms against 0.18 ms, the time of making a thread and an encoder. The single-threaded encoder with `LZMA_FULL_FLUSH` every 100 to 65,536 bytes is at 0.91–1.13×.

### The multithreaded decoder

`--threads N` without `--compress` decodes the Streams of liblzma's threaded encoder with each threaded decoder. Silesia at presets 0 and 6, best of three rounds, on x86-64 where liblzma's range decoder is assembly, November 2026: 0.93× with 1 thread (0.90–1.02×) and 0.94× with 16 (0.89–1.01×), where they were 0.81× with 1, 4 and 16. So the threads add nothing to the gap of the decoder above; `mozilla` at preset 0 goes from 132 MB/s to 1,530 MB/s (liblzma 140 and 1,660), and a preset's big Blocks make fewer threads useful at preset 6, as for liblzma.

Small Blocks cost more than they cost liblzma, which keeps a worker's decoder from one Block to the next where the port makes a new one: 1 MB in Blocks of 4,096 bytes takes 3.9 ms in one thread against 2.9 ms and 1.1 ms in four against 0.76 ms (0.69–0.75×), in Blocks of 100 bytes 0.88–0.93×. This is left to do, as for the encoders above.

### The filters

`--filter x86`, `arm64`, `delta:2` and so on put a filter before LZMA2, and the same files are measured without one beside them. Compression with x86 (`ooffice`, `samba`) and with delta at distance 2 (`x-ray`, `sao`), at presets 0 and 6, is at 0.96–1.08× liblzma. Decompression stays at the LZMA decoder's ratio above: with each of the eight BCJ filters, `mozilla` at preset 0 decodes at 0.79–0.81×, as it does without one (0.79×); and with delta at distances 1, 2 and 4, `x-ray`, `sao` and `mozilla` decode at 0.72–0.81×, as they do without it (0.74–0.79×).

The filters themselves are as fast as liblzma's or faster. liblzma 5.8's single-call functions run at 1.2–1.5× (x86), 1.0–1.3× (ARM64) and 1.0–1.6× (RISC-V) liblzma's speed on `mozilla` and on the ARM64 and RISC-V libraries of Android's NDK, and delta's loops at 1.7× or more. Two loops are written differently for it, with the same results (`Differs from liblzma, without a difference to see`): ARM64's conversions are functions that are not inlined, because LLVM vectorized the loop and made it 2–2.7× slower (liblzma turns vectorization off for Clang there, for the same reason; Rust cannot); and delta's decoder adds the byte `distance` back from the buffer rather than from its history, and at distance 1 from a register, which took it from 0.6 GB/s to 4.8 GB/s at that distance.

## Following new releases

The release followed until now is kept in the [mirror of upstream sources](../testdata/README.md#the-upstream-sources-mirrored), to compare the new one with even once its URL is gone. The new release's source set goes into the manifest and the mirror: `python3 scripts/testdata.py mirror --set <name>`.

When XZ Utils releases a new version:

1. Diff the two tags' `src/liblzma` and port each change.
2. Update `UPSTREAM_VERSION`, `version_number()`, the release in `testdata/manifest.json`, and the `liblzma-sys` version that bundles it.
3. Run everything again.
