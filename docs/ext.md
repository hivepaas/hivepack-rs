# ext2, ext3, ext4: where most of what anyone wants is

`hivepack::ext` reads ext2, ext3 and ext4, read-only. It is the third layer of [issue #225](https://github.com/hivepaas/hivepack-rs/issues/225) and the one with most of the value in it: a Raspberry Pi's root, WSL2's `ext4.vhdx`, a Linux machine's QCOW2, the second partition of every card that boots Linux.

**It is not a port.** The layout is what the kernel's own documentation and e2fsprogs' on-disk description give. Linux's reader is GPL-2.0 and nothing here needed it; the repository's MIT license covers the module, as it covers [`image`](image.md) and [`fat`](fat.md).

It reads a [`Disk`](image.md), so a partition is read by handing it `Part::new(&disk, part.at, part.size)` and a file holding a file system as it is by handing it the file.

## The rules it follows

- **Which of the three it is, is not written anywhere.** A file system says what it *needs*, not what it is called, so the name is read off the features: any feature ext4 brought (extents, 64-bit block numbers, flexible groups, metadata checksums, and the rest) makes it ext4; a journal and nothing newer makes it ext3; neither makes it ext2. That is how `blkid` reads it.
- **A read-only reader may ignore the read-only features, and that is what the field is for** — all but two. **bigalloc** is kept there and changes what every number of blocks in the file system is counted in, so it is refused rather than read as blocks. **huge_file** and **large_file** change how long a file may be, and are read rather than passed over. Everything else in that field is passed over by design, which is why a file system with checksums, quotas, project identifiers or verity is read without knowing any of them.
- **An incompatible feature that is not known at all is refused.** What it changes may be where the data is, so a bit outside the list is not a thing to guess at. Of the ones that are known: **compression** (which no released Linux ever wrote), **encryption**, **group descriptors spread over the file system** and **a journal of another file system** are each refused by name.
- **A journal that was written and never replayed is refused.** The `recover` bit says the file system has not yet become what its journal says it should; reading it would answer what it held before, and replaying the journal is a write. `e2fsck` clears that bit, and a file system that was unmounted cleanly does not have it.
- **A file's blocks are found two ways, and both are read.** ext2 kept twelve block numbers in the inode, then a block of numbers, then a block of blocks of numbers, then one deeper again; ext4 keeps a tree of extents, each saying a run of blocks in one entry. A tree is walked to its leaf for each read, and a node with no signature of its own, more entries than it has room for, or deeper than the format allows, is an error rather than whatever lies at the block it names.
- **A hole reads as zeroes**, because that is what is in it. A file may be longer than the blocks written for it — `truncate` makes one, and so does writing at an offset — and every number of 0 in a map, every block of numbers that was never allocated, and every extent the file system says was allocated and never written, all read as zeroes.
- **Blocks that follow one another are read in one go.** Each read asks where a logical block is and how many after it lie the same way, so a file written in one piece is one read of the disk however the map is shaped.
- **A name is bytes.** Linux puts no meaning on a name beyond `/` and the byte that ends a string, so names and paths are `Vec<u8>`; making text of one would answer a name that is not the file's. A file system built here holds `not\xffutf8.txt` for that reason.
- **A directory is read record by record, and a record of inode 0 is read over.** That is how a file system marks room nothing uses any more — and it is also what the blocks of a directory's own hash index look like, and what the record holding a block's checksum is. So reading a directory this way reads what is in it and nothing else, whichever of those a block turns out to be, and the hash index is never needed.
- **`.` and `..` are not entries**; giving them out would walk a directory into its own parent for ever.
- **A record says what it names, and an old ext2 does not.** Where the `filetype` feature is off the record says nothing, and the inode is what tells; where it is on, what the record says and what the inode says are both read, and a test asserts they agree.
- **A file small enough is kept in its own inode, and is read from there.** `mke2fs -O inline_data` writes such a file system: the first 60 bytes go where the block numbers would be, the rest goes in the attribute the file system calls `system.data`, and the file is given no blocks at all. A small **directory** goes there too, and is shaped differently — its records are one run rather than blocks of them, the four bytes in front of them hold the inode it is in (which stand for its `..`), and its `.` is written nowhere.

  `system.data` is not given out as an attribute of the file. It is the file's own data, and a reader that handed it over would hand the data over twice; whatever put the file back would write its bytes beside it as well as in it.
- **A symbolic link's target is in the inode itself where it is short enough** — under 60 bytes, in the room the block numbers would take — and in a block of its own where it is not. Both are read.
- **Extended attributes are in two places, and both are read.** The ones that fit go in the room left over in the inode, past the fields it says were written; the rest go in a block of its own that the inode points at. A value too long even for a block is given an inode of its own, and is read from there. Both regions are read, the inode's first, as a system reading them does.

  The file system keeps the common beginnings of a name as a number — 1 for `user.`, 4 for `trusted.`, 6 for `security.`, 7 for `system.` — so that they cost one byte, and three numbers stand for whole names rather than beginnings (the two kinds of POSIX access control list, and the rich one). What comes back is the whole name with the beginning put back on, which is the name a system shows. A number nothing is known for leaves the name as it lies, which is what the kernel does with one.

  This is where a system keeps a file's SELinux label, the capabilities a program is given and its access control lists, so an archiver that means to put a tree back as it was needs them.
- **An inode's times are UTC**, because ext has always held seconds from the epoch; there is nothing to decide, unlike a FAT time. An inode with room past its first 128 bytes also holds nanoseconds and when the file was made, and two bits of the extra field carry what the seconds have run out of room for.
- **Nothing is cached.** A block of numbers or a node of a tree is read when it is wanted. The `Disk` underneath may cache as it likes.
- **Checksums are not checked.** ext4 may carry a CRC-32C of its superblock, its group descriptors, its inodes, its extent nodes and its directory blocks. A reader that only reads cannot repair what one would catch, and what tells an ext file system here is the signature and a layout that holds together — the root being inode 2 and a directory among other things. This is a choice, and it is the one thing in this module a future change might take back.

## What it refuses

- A file with no superblock signature: `Unrecognized`. One with the signature and nothing behind it: `Says`.
- A block size the format has not got, no blocks or no inodes, groups of no blocks or no inodes, data before the superblock, an inode smaller than 128 bytes or larger than a block, a file system longer than the disk it is on: `Says`.
- `Needs(Journal)`, `Needs(Encrypted)`, `Needs(MetaGroups)`, `Needs(BigAlloc)`, `Needs(Compression)`, `Needs(Feature)`, each as above.
- A file that says its data is in its own inode and is longer than what is there — the 60 bytes and the attribute the rest is in do not add up to the length the inode gives: `Inline`.
- A block past the end of the file system: `PastTheEnd { block }`. An extent tree that cannot be walked: `ExtentTree`. A directory whose records run past its blocks: `Records`. Extended attributes that cannot be read — a block with no signature of its own, an entry running past the room it is in, an entry of no name, a value that is not where it says: `Xattrs`.
- A directory of more than is read, or a tree deeper than 1024, or a directory that leads back into one already walked: `TooMany` and `TooDeep`.

## How it is checked

`crates/hivepack/tests/ext.rs`, in two halves.

- **Against `mke2fs -d`, which puts a folder into a new file system.** A tree of a short file, an empty one, one of 400 KB (longer than the twelve numbers in an inode and longer than one block of numbers after them, so all three levels of the map are read), a file with holes near its front and near its end, a folder two deep, both kinds of symbolic link, a name that is not UTF-8, and two names for one file — put in, and read back out: every path, every file's bytes, every link's target, in reads of 3571 bytes so that none lines up with a block. For ext2, ext3 and ext4, and then for eight layouts of them: 128-byte inodes (which have no room for nanoseconds or for when a file was made), records that say nothing about what they name, group descriptors of 32 bytes and of 64, an ext4 whose files are mapped as ext2's were, an ext4 without metadata checksums, blocks of 1, 2 and 4 KiB, and inodes of 1024 bytes. The hard link is checked to be one inode with two names.
- **Against `debugfs`, which is another reader of the format and not this one.** For several paths, what it says about the inode — the number, the size, the owner, the group, the links and the mode — against what this reads; and two files **dumped by its own reader**, byte for byte against what this one reads, one of them the file with holes.
- **`e2fsck -fn` over every image**, both the ones `mke2fs` wrote and the ones built by hand.
- **A tool being installed is not the same as it being able, and its age is the usual reason.** CI's s390x container has e2fsprogs 1.42.13, from May 2015, and three things follow from that alone: `mke2fs -d`, which fills a file system from a folder, came with 1.43, so the older one answers its usage message; that `e2fsck` does not know `inline_data` and refuses to look at such an image at all, saying to get a newer version, so it has not judged it; and it takes `-O meta_bg`, writes a file system without the feature and says nothing, leaving the reader nothing to refuse.

  So each test asks for the one thing it needs rather than for the tool: whether this `mke2fs` can fill from a folder is asked by filling a small file system from an empty one; whether the feature an option asked for was really written is read out of the superblock's own feature words; and an `e2fsck` that says the image carries features it does not know has not checked it, so there is nothing in what it said to assert. Where any of those answers no the test says so and passes, and the modern tools in the other jobs are what keep that honest — the hand-built half is checked everywhere.
- **Data kept in inodes against `mke2fs -O inline_data`**: a file short enough for the 60 bytes in the inode, one that needs the attribute as well, one far too long for either, and a folder — each read for its bytes or its records, with what the file system gave no blocks at all asserted to have none, so that the layout is known to be taken rather than hoped to be.

  That tree is its own rather than the one the layouts above share, because **`mke2fs -O inline_data -d` does not write the tree it is given**: a file with a hole at its end comes out shorter than the file that went in — 880640 bytes for one of 900000 — and `debugfs` says the same of the image, so it is the tool and not this reader. The same `mke2fs` without the feature writes the length the file has.
- **Extended attributes against `debugfs`, which is what sets them here.** `setfattr` is not installed everywhere and `mke2fs -d` can only copy what the folder it is given already has, so `debugfs`' own `ea_set` writes them: two short ones on one file and a 300-byte one on another, then read back and compared with what was set, with the names `ea_list` gives and the value `ea_get` reads with its own reader.

  What `debugfs` writes always goes in a block of its own and never in the room left over in the inode, so that half is checked by hand instead: the file systems built below carry two attributes in an inode's own room and two in a block, the first of them longer than any inode could have held.
- **File systems built byte by byte**, which is what CI checks the reader against where no tool is installed: one block group, blocks of 1 KiB, with 128-, 256- and 512-byte inodes and with the files mapped both ways. Each holds a short file, a file of 300 blocks (direct, single indirect and double indirect, or one extent), a file of holes with three pieces in it, a file of six pieces — **more extents than an inode has room for, so the tree has a depth of its own** — both kinds of symbolic link, a name that is not UTF-8, a folder with a file in it, and `lost+found`, which `e2fsck` wants to find.

  Running `e2fsck` over those is what makes this half worth having, and it earned itself three times. The first build was sound but for a free-block count one short of the truth, which `e2fsck` named while saying nothing about the bitmap — so the bitmap was right and only the number stored beside it was wrong. Then the attributes in a block drew `i_file_acl for inode 13 is 317, should be zero`, because a file system has to say in its own features that its inodes may have attributes at all before one may point at such a block. And it checks the hash of every entry, which the test leans on: a hash deliberately set to 1 is answered with *extended attribute in inode 13 has a hash (1) which is invalid*, so the algorithm e2fsprogs hashes with, written again here, is checked rather than assumed.

  Then: paths looked up by the bytes of their names, and case that is case where FAT would have found it either way; what a thing is not (a directory asked for as a file, an inode of 0, an inode past the last one); reads in pieces of 1, 7, 1023, 1024, 1025, 4096 and 100003 bytes, with a seek into a hole and a seek from the end; files that are not file systems; nine layouts the format has not got; six features refused as the superblock says them; and an extent tree robbed of its signature, one saying more entries than it has room for, and one pointing past the end of the file system.

- **A fuzzer feeds it anything** (`fuzz/fuzz_targets/ext.rs`). The whole file system walked, every file read, every link followed, every inode's extended attributes read, every path looked up again. What is read is read twice, in pieces of different sizes the input itself picks, and the two must agree: a reader that is right only for the order it was asked in is a bug, as is a panic. The corpus is seeded with the smallest images the tools will write, because a superblock that fails its own checks is refused in the first bytes and nothing behind it is ever reached.
